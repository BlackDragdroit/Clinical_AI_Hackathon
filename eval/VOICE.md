# Voice evaluation (CPU, synthetic dictation)

Generated by `python -m eval.voice_eval report` from `eval/results/voice_<set>_<backend>.json`.

**Pipeline.** Dictated request items (`style == "dictated"`) -> Piper TTS (`piper-tts`, voices `de_DE-thorsten-medium` / `en_US-lessac-medium` from `rhasspy/piper-voices`, resampled to 16 kHz mono) -> CPU ASR -> `request_job.run(transcript, MemoryDirectory(patients.json), use_llm=False)` (rules only) -> same scoring as `eval/run_eval.py`. Row `text` runs the request job on the item's own text (perfect ASR), so the gap to it is what ASR costs.

**Caveats.** One synthetic voice per language, clean audio, no noise, no accents: this is a best case for ASR, not a field estimate (see `eval/data/voice_script_*.md` for recording real voices). Timings are on a shared Windows laptop CPU with every model limited to 3 threads while another benchmark (llama.cpp, ~8 threads) was running -- latency/RTF are inflated and only comparable within this run. WER is against the dictated wording ("punkt", spelled digits), so an ASR that writes `0660…` or `a.b@c.example` pays WER for a correct hearing; contact exact is the number that matters.

## Findings (run of 2026-10-30, test set, rules only)

- **The rules-only baseline is already low on dictation.** On the item text itself, 40 % of the 120 dictated requests come out fully correct. Recipient is right in only 24 % and patient in 38 %, because the rules miss lower-case spoken names. Contact is right in 90 %.
- **ASR costs a further 10–20 points of full-request accuracy.** Parakeet: 23 % (n=120) against 40 %. Whisper small: 30 % against 45 % (n=60). German turbo: 23 % against 40 % (n=30). The CIs overlap heavily between backends, so this run does **not** rank them. Contact is where it hurts: 90 % becomes 34–40 %.
- **E-mails fail safe; phones do not.** A lost e-mail almost always becomes "no e-mail found" (Parakeet 46 none / 0 wrong). The cause is that the spoken symbols get mangled or glued: "at" is heard as "Art"/"Adler", "punkt" sticks to a word ("Punktbauer", "Donaupunkt"), lab domains are misheard ("zentrallabor dash donau" becomes "Central Aberdash Donnell"), and Whisper puts commas between every token. Phone failures are mostly *wrong values*. Both ASRs write "plus 436 643 209830": the digits are right, but the rules drop the "+". Parakeet also stutters on repeated digits ("six six" becomes "six six six six six six six") and collapses runs of zeros ("0660000101" becomes "06 6000101"). That last one became a **silent error** (`test-0109`, ready with a wrong number). Whisper hears "null" as "Müll".
- **Safety.** There was no wrong-patient pick on any rung. Silent errors: Parakeet 2/120 (wrong phone; recipient "Eigner" instead of "Aigner"), Whisper small 2/60, turbo 2/30. The text baseline has 2/120.
- **The punctuation cleanup experiment (`--clean`) is not a fix.** It raises patient matches, but it also raises silent errors (Whisper small 2 → 7 of 60) and turns "no e-mail" into *wrong* e-mails (2 → 9).
- **Speed (3 contended threads).** Parakeet takes 2.8 s per ~11 s clip (RTF 0.23), Whisper small 11 s (0.95), German turbo 33 s (2.8). Only Parakeet is usable interactively on this CPU.
- **Cheap engine-side wins, in priority order:**
  1. Treat "plus" followed by digit groups as "+".
  2. Rebuild e-mails tolerantly: ignore commas between tokens; accept "Art", "ät" and "add" as `@`; split a glued "punkt"; normalise ß to ss and "Exemple" to example.
  3. Snap the domain to a known sender domain, or else ask.
  4. Never mark ready when a phone number came out of a digit run the ASR may have stuttered on. Read it back instead.
